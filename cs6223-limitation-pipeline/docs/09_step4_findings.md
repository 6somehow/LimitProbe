# Step 4: Integrating Findings (2026-11-11, v2)

The code side (steps 2 + 3b) and paper side (Zhaopeng's handoff package) are combined into Findings for Shanghao to generate tests.
There are four tasks: **deduplication, classification, setting priority, and solving witness_hint**. See `docs/03_codeside_spec.md` §4 for the specification; this page records the implementation, results, and decisions pending from the team.

## How to run

```bash
# 1. Rerun 3b with Zhaopeng's paper_side.json (calls the model; with a cache, only changed parts incur cost)
python scripts/run_pipeline.py --out-dir out/pipeline_ps --seed-cache out/pipeline --parallel 1 --workers 3
# 2. Step 4 (calls the model for deduplication decisions and paper-side conditions; cached in out/step4_cache/, about 16 seconds with all cache hits)
python scripts/run_step4.py              # defaults: --code-dir out/pipeline_ps --out results/step4 --model x-test-2
python scripts/run_step4.py --no-llm     # no model calls: no cross-side merging, no paper-side conditions
python scripts/make_handoff_doc.py       # regenerate results/step4/HANDOFF.md
python -m codeside.cli validate results/step4/*/findings.json
```

Output (`results/step4/`):

| `review_queue.json` | The same Findings, sorted by priority → review status → category, one per line |

Code: `codeside/integrate.py` (deduplication, classification, priority), `codeside/step4_llm.py` (two kinds of LLM decisions),
`codeside/witness.py` (witness_hint solving); tests: `tests/test_step4.py`.

## 1. Deduplication

1. **Within the code side** (no LLM): records in the same function with the same normalized condition and effect are merged (`not (a == b)` and `a != b` are treated as equivalent).
2. **Select candidate pairs** (rules):
   - Paper side × paper side: records in the same group in Zhaopeng's `finding_candidates.json`, or with identical code evidence.
   - Code side × paper side: overlapping code locations.
3. **Decide whether they are the same thing** (LLM, `x-test-2`, temperature 0, prompt `step4-v1`): provide both records' conditions, effects, paper quotes, and original code.
   “The same thing” means the same code behavior that one test can cover. Two different checks in the same function, or a broad design difference and one of its specific checks, count as different.
   Ask up to 3 times per pair, stopping if the first two agree; **two yes votes are required to merge**. Pairs judged the same are merged using union-find.
4. For candidate pairs judged different, add `related (candidate pair, judged different)` to both rationales so they can be viewed together.
5. Zhaopeng's `effect_text` has 63 entries that say “同上……” (original-language quote, meaning “same as above…”). This refers to `local_entry.discrepancy` in the same conformance.json record.
   Expand it before giving it to the LLM or writing the summary; retain the original record in the handoff file.

## 2. Classification (schema v0.2.0, 7 categories)

| Category | Source | When |
|---|---|---|
| `undisclosed` | Code side | 3b not_found; or none of the evidence found counts under the rules below |
| `contradicts_docs` | Code side | 3b contradicted, and the evidence counts |
| `stated_differently` | Code side | 3b boundary_mismatch or weaker (documented, but with different boundaries or a weaker statement) |
| `docs_only` | Code side | 3b found, with evidence only in README / public docstrings / other user documentation |
| `paper_stated` | Code side | 3b found, in the paper or appendix |
| `impl_deviates` | Paper side | 3a deviates |
| `not_implemented` | Paper side | 3a absent |

**There is one rule for whether something counts as documented**: it must be somewhere users will read it—the paper (including appendices), README, other user documentation, or a public function's docstring.
Code comments (including TODO/FIXME), docstrings of functions starting with `_`, and sentences that only state a version number do not count. There is no longer a switch.

When a merged Finding has multiple code-side categories, choose the one that best conveys what the user does not know (contradicts_docs > undisclosed > stated_differently > …).
Paper-side categories are recorded under `paper side also reports` in the rationale.

## 3. Setting priority (consequence × triggerability)

| priority | Condition |
|---|---|
| 3 (direct) | scope is out_of_scope; witness is unreachable (infeasible); review is wrong |
| 1 | category is undisclosed / contradicts_docs, consequence is severe (reject / accuracy / state), and witness can trigger it |
| 2 | As above, but consequence is moderate (path_change / resource / performance) or triggerability is unknown; or category is stated_differently / impl_deviates |
| 3 | Everything else (docs_only, paper_stated, not_implemented, or consequence other) |

- “Can trigger” means witness status is solved / solved_contrast_outside_scope / trigger_only / always.
- `--strict-scope`: unknown scope cannot enter priority 1 (almost no parameter mappings are currently available on the paper side for the four papers, so this is off by default).
- A merged Finding takes the highest priority among its members' categories.
- **Review status** `review`: `worth_testing` / `real_but_minor` / `wrong` / `unreviewed`, initially filled using blind-review labels
  (`results/review/blind_review_labels.json`, blind review by Claude subagents, **not human**, as stated in `review_note`). Only the code side has labels.

## 4. Solving witness_hint (format `witness-v2`)

The goal is one point on each side of the boundary. `trigger` takes the limitation branch; `contrast` is the nearest point that does not.
Both satisfy the path prefix; names mapped by Binding to the paper scope are within scope at both points. For names unconstrained by scope, the paper EvalPoint values are preferred.

```json
{
 "format": "witness-v2",
 "kind": "input_value",              // or event_sequence (effect=state: earlier calls must first set the state to trigger)
 "status": "solved",
 "condition": "q_len != k_len",
 "path_prefix": [],
 "dropped_prefix": [],               // prefixes that could not be translated and were excluded from solving
 "aliases": {"q_len": "q.shape[1]", "k_len": "k.shape[1]"},     // added in v2
 "trigger":  {"q_len": 1, "k_len": 2, "q.shape[1]": 1, "k.shape[1]": 2},
 "contrast": {"q_len": 2, "k_len": 2, "q.shape[1]": 2, "k.shape[1]": 2},
 "atoms": {"q_len": {"kind": "local", "sort": "int"}, "q.shape[1]": {"kind": "derived", "sort": "int"}},
 "from_paper": {"tau": "scope sparse_pattern_threshold_tau: [0.0, 1.0]"},
 "eval_preference": {"tau": 0.1, "block_size": 128},
 "location": "flex_prefill/ops/vertical_slash_attention.py:265",
 "function": "flex_prefill/ops/vertical_slash_attention.py::..."
}
```

**Changes from v1 to v2**

1. **Aliases**: find local variables in the function containing the check that are assigned only once, before the check (`q_len = q.shape[1]`, `b, n, h, d = q.shape`),
   and add equalities such as `q_len == q.shape[1]`. The two names then have the same value, so the test can construct a tensor using `q.shape[1]`.
   - The path prefix can include conditions from functions at different levels of the call chain (the caller's `q` and the callee's `q` are not the same tensor). Aliases are used only at a single level:
     when the check is in the entry function or there is no path prefix. Otherwise, aliases are listed in `aliases_not_applied` for reference and excluded from solving.
   - If adding aliases makes the problem unsatisfiable, remove them and solve again, recording them in `aliases_dropped`.
2. **Paper-side conditions**: the LLM reads the paper-side record and cited code and writes a Python condition for the inputs under which the difference appears, or answers
   `always` (appears on every call, e.g. a different formula or missing functionality) / `not_input` (depends on hardware, build, etc.).
   **Check against code**: every name in the condition must appear in the cited code lines, or it is rejected (`rejected`). Accepted conditions go to the same solver,
   with `condition_source` recorded.

`atoms` explains each name and how the test should construct it:

| kind | Example | Meaning |
|---|---|---|
| input | `head_dim` | Ordinary name; assign a value directly |
| local | `q_len` (with an alias) | Local variable whose value is determined by the expression in `aliases` |
| derived | `q.shape[1]`, `len(x)`, `self.layer_id` | Value computed from input; the test must construct this value |
| predicate | `is_flash_attn_2_available()`, `x is None` | Boolean value the test must arrange (mock or select input) |
| category | `q.dtype` (compared with `torch.bfloat16`) | String or enum; `{"not_in": [...]}` means any value other than those listed |

| status | Meaning |
|---|---|
| solved | Both points exist |
| solved_contrast_outside_scope | contrast can only be outside the paper scope |
| trigger_only | The condition always holds on the path; there is no contrast |
| always | Paper side: appears every time execution reaches the cited code; any input that reaches it is a witness |
| infeasible | The condition contradicts the path prefix and is unreachable from the entry (priority reduced to 3) |
| untranslatable | The condition is not a translatable Python expression |
| unknown | Solver timed out |
| no_condition | Paper side: the LLM provided no usable condition (not_input or failed the check); only code location and text remain |

`closest: false` means fallback solving was used (including nonlinear terms). Both points are valid, but are not guaranteed to be closest.

### Added 2026-11-15: effect label checks, call chains, entry names, and stable IDs

The format name remains `witness-v2`; only fields are added, and existing fields retain their meanings. These address four requests in `checklimits/REQUESTS_TO_STEP4.md` and W1–W3 in `E2E_PLAN.md`.

**1. Effect labels must match the target statement (W2, `codeside/effect_anchor.py`, AST only)**

The test side checks the effect at the target location: `reject` requires the target statement itself to be able to raise an exception; `path_change` / `state` require an `if` / `while` target.
Route B sometimes labels a statement that is merely the beginning with “the program eventually rejected.” Step 4 now checks and corrects this first, recording corrections in the Limitation's `notes`
and `effect_checks` in `findings.report.json`:

| Label | Target statement | Action |
|---|---|---|
| reject | `assert`, `raise`, or `if` / `while` / `for` / `with` / `try` with a `raise` in its body | Unchanged |
| reject | An `except X:` line with a `raise` in its handler | Move target to that `raise` |
| reject | Other (an `if` / `while` with no `raise` in its body, call, assignment) | Change to `other` and record the reason |
| path_change / state | `if` / `while` | Unchanged |
| path_change / state | Inside an `if` / `while` body whose branch condition is this record's condition | Move target to that branch |
| path_change / state | Other | Change to `other` and record the reason (the effect is a value change and needs a differential check) |

The test side does not currently judge `other` entries; reports can quote the reason recorded here directly.

Under the test-side convention (item 5 in `checklimits/REQUESTS_TO_STEP4.md`), `reject` on an `if` / `while` without a `raise` in its body changes to
`other`, not `path_change`: “the branch was executed” is weaker than “the input was rejected,” and a `yes` verdict would be read as confirming rejection.

When the target moves, `witness_hint` also contains `effect_location` (the statement that actually produces the effect, i.e. the new `code_evidence[0]`),
`labelled_location` (the location originally labelled), and `effect_location_reason`.

**2. Call chains and argument mapping (W1, `codeside/callgraph.py`)**

`witness_hint` adds:

```json
{
 "call_chain_status": "resolved",      // resolved | entry_is_target | module_level | not_found
 "call_chain": ["…::flex_prefill_attention", "…::get_active_blocks", "…::triton_bnhd_pool"],
 "call_sites": [
  {"caller": "…::flex_prefill_attention", "callee": "…::get_active_blocks", "line": 1856,
   "resolved_by": "direct", "args": {"q": "q", "k": "k", "block_size": "block_size", "…": "…"}},
  {"caller": "…::get_active_blocks", "callee": "…::triton_bnhd_pool", "line": 1719,
   "resolved_by": "direct", "args": {"x": "k", "kernel_size": "block_size"}}],
 "other_chains": [["…"]],              // other call chains (e.g. a second call site)
 "uncertain_steps": ["…"],             // calls resolved by guesswork, see below
 "calls_entry": ["…"]                  // when not_found: this function calls the entry
}
```

Call resolution methods (`resolved_by`): `direct` (same file, imported functions, `Class(...)`, or `obj.m()` after `obj = Class(...)`),
`self`, and `import` (`module.f()`) are certain; `unique_name` (method name unique in the repository), `override` (a subclass overrides `self.m()`),
and `reference` (a nested function is passed out by its parent instead of called) are guesses and are listed in `uncertain_steps`.
Calls with unknown type and non-unique method names (`layer(x)`, multiple `forward` methods) cannot be resolved; the target is `not_found`, without guessing.
An entry function in the same file as the target is preferred (consistent with the test-side entry selection rule).

**3. Replace callee names with entry function names (W3, `codeside/chain_bind.py`)**

Translate names upward at each level of the call chain: replace local variables with their definitions (`b, n, h, d = x.shape` gives `d -> x.shape[3]`),
and formal parameters with arguments at the call site (`x -> k`), up to the entry function. During solving, rewrite the condition and each path prefix using entry names and add them as constraints
(the originals are also retained, so the hint still gives values for names used in the code). The function level of a path prefix is determined from the source:
which function on the call chain has that condition before its call site. The result is recorded in `entry_terms`:

```json
"entry_terms": {"condition": "not k.shape[3] in {16, 32, 64, 128}",
                "path_prefix": {"head_dim in {16, 32, 64, 128}": "k.shape[3] in {16, 32, 64, 128}"},
                "names": {"d": "k.shape[3]", "q_len": "q.shape[1]"}}
```

If these constraints make the problem unsatisfiable, the target is unreachable from the entry through this call chain: `status: infeasible`, `infeasible_because: call_chain`
(priority 3). If there are multiple call chains, each is tried; all must be unsatisfiable for this conclusion. If a call chain contains a guessed step, do not draw this conclusion; fall back to solving without the call chain,
and record `entry_terms_dropped`.

Cases where names are not replaced (avoid incorrect replacements): a local variable is assigned in a loop or branch; the right-hand side of its definition is modified after the definition; a formal parameter is reassigned before use
(`q = q.transpose(1, 2)`); the call uses `*args` / `**kwargs`; or the same name has different meanings at different levels of the call chain
(recorded in `ambiguous_names`).

**4. Finding IDs remain stable across runs**

The test side archives results by finding_id. When step 4 is rerun, a Finding made up of the same set of Limitations retains its previous ID
(read from the existing `findings.json` in the output directory); a new Finding takes the next available ID. The file remains ordered by priority.

**5. Snippet convention for multiline statements**

Step 4 rewrites each code-side Limitation's `snippet` into a consistent form (`codeside/effect_anchor.py::canonical_snippet`),
the same for routes A and B:

| Statement | snippet |
|---|---|
| `assert` | `assert <条件>` (remove the message; `<条件>` is an original-language quote of the condition placeholder) |
| `if` / `while` (including `elif`) | `if <条件>:` / `while <条件>:`, header only (`<条件>` is an original-language quote of the condition placeholder) |
| Other | First line of `ast.unparse(语句)` (`语句` is an original-language quote of the statement placeholder) |

Each is one line, with extra parentheses removed, at most 200 characters. Previously route B's snippet was the first line of the source verbatim, leaving only `if (` for multiline statements;
route A's assert included the message. That no longer happens. Consumers should compare parsed conditions, not literal text. Any future change to this convention will be announced first.

**6. Two forms with no contrast point (`trigger_only`)**

Route B has two forms of condition that leave a witness without contrast, causing the test side to record `witness_unusable`. Rewrite them before solving (`witness.decision`):

* The condition is also copied into its own path prefix (the last item): remove it and record `prefix_dropped`. Earlier prefix items with the same text come from other functions
  on the call chain (such as the entry function's own check) and are retained.
* The condition is `True` (an unconditional `raise` in a branch): the actual decision is the innermost path prefix item. Use it as the condition and record the original in `condition_original`.

All 6 original `trigger_only` cases across the five papers gained a contrast as a result (code-side nnsmith-F001 and minference-F006; the other 4 are paper-side).
