## LS2-01-L1 (flexprefill) - applicability_limitation - mechanism_reported_consequence_inferred
**Selecting Vertical-Slash indexes from the last query block does not guarantee coverage for mid-sequence queries**

For Vertical-Slash heads, which the paper reports are the large majority of heads, FlexPrefill computes attention only for the last block_size (128) queries, keeps the vertical and slash lines that reach cumulative mass gamma for that block, and then applies those lines to every query in the prompt. The gamma target is therefore checked only for the end-of-prompt queries; the paper gives no coverage guarantee for queries elsewhere in the sequence. This fits workloads where the trailing queries, such as a final question, decide the answer. It may fit less well when accuracy depends on long-range attention from mid-sequence tokens to keys the last block does not attend to (for example, multi-hop chains inside the document). The paper's own ablation shows that index quality depends strongly on which queries serve as the proxy, but the ablation cannot tell which property of the last block makes it work.

- Critical link: The key step is whether, in real workloads, mid-sequence queries need long-range keys that the last block's lines miss, and whether that changes final outputs after dense decoding. Table 8 shows strong sensitivity to the proxy's position, but the effect is confounded with causal reach, so it does not show that prompt layout or task structure matters.
- Conditions: The head is classified as Vertical-Slash (the common case per Appendix H).; Task-relevant long-range dependencies of mid-sequence tokens point to keys that receive little attention mass from the last query block.; Those mid-sequence representations affect the answer even though decoding is dense.; Comparison at the same gamma and minimum-budget settings as a full-attention or per-query-coverage baseline.
- Defeaters: The retained first/last key blocks, slash lines, and the 1024-token minimum budget already cover the keys mid-sequence queries need.; Vertical lines that are important are shared across query positions (e.g., sinks and salient tokens), so the last block's selection transfers well.; Benchmarks with multi-hop tracing and aggregation (RULER) show no degradation at matched gamma, as the paper's averages suggest.; A variant that uses several representative blocks gives the same accuracy as the last-block version.
- Locations: §3 Cumulative-Attention Based Index Selection; Algorithm 3; PDF pages 5-6; §4.1 Implementation Details; PDF page 7; Appendix F.3; Table 8; PDF page 23; Appendix H; Figure 8; PDF page 26

## LS2-01-L2 (flexprefill) - method_shortcoming - mixed_reported_and_inferred
**A fixed cumulative-attention threshold does not guarantee keeping low-mass but decisive keys, especially at long context**

FlexPrefill picks, per head, the smallest set of blocks or lines whose normalized attention mass reaches gamma. The paper justifies this with an output-error bound proportional to (1 - a_S). The objective treats attention mass as a stand-in for importance, so any key whose share of mass falls in the discarded 1 - gamma tail can be dropped, however decisive it is. With one gamma for all context lengths, longer prompts spread the tail over more keys. Tasks whose answer depends on many weakly attended keys, or on one key among many similar distractors, may then lose accuracy faster at long context than the average score suggests. The paper's own gamma sweep shows degradation concentrated at 128k, but the paper does not explain this pattern.

- Critical link: The key question is whether the length-dependent and task-dependent losses the paper measures (Table 5 at 128k, Retr.KV in Table 2) are actually caused by decisive low-mass keys falling in the dropped tail, rather than by pooled-estimate error or the model's own long-context weakness. The paper reports the losses but does not attribute them.
- Conditions: Decisive keys receive low individual attention mass relative to many competing keys in the relevant heads.; Long context (e.g., 64k-128k) with a gamma fixed across lengths.; Comparison against full attention at the same model and prompts, with the minimum-budget setting held constant.
- Defeaters: Measured per-head attention shows decisive keys consistently ranked within the gamma set at long context.; Degradation at low gamma is fully explained by pooled-estimation error rather than tail truncation.; Redundancy across heads/layers ensures at least one head retains each decisive key.; The minimum budget (1024 tokens, first/last blocks) already covers the relevant keys.
- Locations: §3 Cumulative-Attention Based Index Selection; Eq. 3; Algorithm 4; PDF pages 5-6; Appendix A; Eq. 6; PDF page 19; §4.2; Table 2; PDF page 8; Appendix E; Table 5; PDF page 22; Appendix F.4-F.5; Tables 9-10; PDF pages 23-24; Appendix J; PDF page 26

## LS2-02-L1 (flexposit) - method_shortcoming - mixed_reported_and_inferred
**Allocating bits by WikiText-2 perplexity sensitivity does not guarantee iso-quality with BitMoD beyond perplexity**

FlexPosit ranks channel windows by the drop in end-to-end perplexity when that one window is upgraded alone. It then picks the 'PEB' operating point, at which all hardware comparisons are made, as the lowest precision matching BitMoD's WikiText-2 perplexity. So the same perplexity signal serves as both the optimization objective and the fairness criterion. Algorithm 2's profiling dataset is not specified as disjoint from the WikiText-2 evaluation. Downstream accuracy is reported only for FlexPosit, not for BitMoD, at the matched points. Where perplexity-sensitive windows differ from task-sensitive ones, or where profiling overlaps evaluation, iso-PPL may overstate iso-quality. The headline 1.8x throughput / 1.2x energy gains over BitMoD would then be measured at points that are not iso-accuracy on downstream tasks.

- Critical link: Whether FlexPosit at PEB and BitMoD at 4 b differ on downstream tasks. The paper reports downstream numbers only for FlexPosit, and its LLaMA-2-7B MMLU values below 5 b are several points under FP16.
- Conditions: Downstream-task sensitivity of channel windows differs materially from WikiText-2 perplexity sensitivity, or the profiling set D overlaps the evaluation corpus.; BitMoD 4 b keeps downstream accuracy better than FlexPosit at the same WikiText-2 PPL.; Latency stays roughly proportional to virtual precision over the range needed to close any gap.
- Defeaters: D is a held-out corpus disjoint from WikiText-2 evaluation.; BitMoD 4 b downstream accuracy measured under the same protocol is no better than FlexPosit's at PEB.; Profiling on a task-mixture set gives essentially the same window ranking.
- Locations: §IV-B Perplexity-Driven Sensitivity Profiling; Algorithm 2; PDF pages 5-6; §VI-A Iso-area and Iso-PPL Evaluation Setup; PDF page 9; Table II; Fig. 9; PDF pages 9-10; §VI-B Downstream task accuracy; Table V; PDF page 11; Fig. 11; PDF page 12

## LS2-02-L2 (flexposit) - applicability_limitation - inferred
**The compute-density advantage may not carry over to memory-bound, single-token autoregressive decode**

FlexPosit's speedups come from packing more bit-serial compute into a fixed area. Each 4-way MAC cluster reuses one decoded weight term across four distinct activations. The hardware evaluation defaults to batch 1 with a 256-token input sequence, which gives each weight many activation rows to reuse. In autoregressive decode at small batch, each weight is used by only one or a few activation rows per step. Array rows and cluster lanes then go idle, and latency is set mostly by weight bytes streamed from DRAM rather than by compute density. In that regime FlexPosit's PEB weights (4.1-5.0 b plus a per-channel scale index) are no smaller than BitMoD's 4 b. So the reported latency advantage over BitMoD may shrink or reverse for decode-dominated edge workloads. The paper does not separate prefill from decode.

- Critical link: Whether the 256-token-sequence evaluation corresponds to a prefill-like GEMM with M of about 256, and what share of real edge inference time is spent in small-M decode. The paper does not specify this.
- Conditions: The workload's time is dominated by autoregressive decode with small batch (M much smaller than the array rows times 4 lanes).; DRAM bandwidth is the binding constraint for decode GEMMs on the modeled DDR4 system.; The comparison is against a BitMoD configuration at 4 b with comparable memory systems.
- Defeaters: The 256-token evaluation already models per-token decode steps, and the gains persist.; Decode is batched widely enough (or uses speculative/multi-token decoding) to keep M large.; Weight-buffer reuse or on-chip residency makes decode compute-bound for the evaluated model sizes.
- Locations: §V-A Dataflow; §V-B 4-Way MAC Clusters; Fig. 6; PDF pages 6-7; §VI-A Hardware Implementation; PDF page 9; §VI-C Latency, energy, and EDP comparison; Fig. 11; PDF pages 12-13; §VI-C Workload sensitivity; Table X; PDF page 13

## LS2-03-L1 (qoserve) - method_shortcoming - mechanism_reported_consequence_inferred
**Cumulative per-token deadlines let dynamic chunking reintroduce long inter-token gaps while reporting TBT compliance**

QoServe sets the n-th token's deadline to arrival + SLO_TTFT + (n-1)*SLO_TBT, defines slack as the time left before the next token's deadline, and enlarges chunks whenever slack exists. A request whose first token arrives well before its TTFT deadline has slack of up to the TTFT margin. The paper explicitly uses that slack to run larger chunks while the request is decoding. Larger chunks lengthen iterations (Fig. 4), so the actual gaps between consecutive tokens can exceed SLO_TBT many times over while every cumulative deadline is still met. The near-zero TBT violation figure is therefore compliance with cumulative deadlines. It does not bound per-token gaps, which is what Sarathi-style fixed chunking protects. If users perceive per-token fluency, generation stalls can come back under QoServe.

- Critical link: How much accumulated slack is actually spent while interactive requests are mid-decode, and therefore how large the longest inter-token gaps get. The paper reports violations against deadlines, not the distribution of raw gaps.
- Conditions: Interactive requests finish prefill well before their TTFT deadline, so they accumulate slack.; The scheduler spends that slack on chunks whose iteration time exceeds SLO_TBT while those requests are decoding.; The user experience depends on the gap between individual tokens, not only on the cumulative arrival schedule.
- Defeaters: The implementation also caps each iteration's latency at SLO_TBT for decoding interactive requests.; Clients buffer and smooth token output, so per-gap stalls are invisible.; Measured raw inter-token gaps (P99 or max TBT) stay near SLO_TBT.
- Locations: §3.2 Eq. 1-2; §3.3; Fig. 4; PDF page 5; §3.5; Fig. 6; PDF pages 6-7; §4.1.4; Fig. 9; PDF pages 9-10; §4.2; PDF page 10

## LS2-03-L2 (qoserve) - applicability_limitation - mixed_reported_and_inferred
**Priority and relegation for non-interactive requests rely on TTLT deadlines far exceeding processing time**

QoServe cannot know a non-interactive request's decode length. It approximates the length from per-application history plus two standard deviations, and justifies this by noting that TTLT deadlines usually far exceed actual processing time. The relegation check runs at prefill selection (already violated, or about to violate in the current iteration), and decoding requests are never preempted. So a non-interactive request that will miss its TTLT because of decode time is not caught while relegation is still possible. The priority ordering and graceful degradation for this class are therefore reliable only when TTLT slack is much larger than the variation in decode time, as with the 600 s/1800 s tiers evaluated. With tighter TTLT targets, heavy-tailed output lengths, or a shift in an application's output distribution, misordering and late, unrecoverable violations may increase.

- Critical link: The ratio of TTLT slack to the spread of decode time. The paper's evaluated tiers have very large ratios, so the estimate's adequacy there may not carry over to tighter targets.
- Conditions: Non-interactive TTLT targets comparable to the request's processing time under load.; Output-length distributions that are heavy-tailed, or that drift relative to the application history.; Overload, where priority order and relegation decide who violates.
- Defeaters: TTLT targets stay at hour/many-minute scale relative to processing time, as evaluated.; Output lengths are capped by max_tokens so tightly that mean + 2 sigma is a safe bound.; A per-request output-length predictor or online refinement (as in Tempo, cited) replaces the history estimate.
- Locations: §3.4 Eq. 5, Eager Relegation, Selective Preemption; Algorithm 1; PDF page 6; §3.6; PDF page 7; Tables 2-3; PDF page 8

## LS2-04-L1 (tessera) - method_shortcoming - mixed_reported_and_inferred
**Min-max partition selection over single-run profiled costs does not guarantee the lowest bottleneck under routing variation**

Tessera's partitioner minimizes the maximum post-overlap edge cost. Each candidate pair's cost is profiled once on a reference device group, and the paper does not state the token-routing distribution used during profiling. At runtime, MoE routing changes MoE compute and All-to-All durations from iteration to iteration, and the paper says this effect is stronger for Qwen3-Next's 10-of-512 routing. If those fluctuations are as large as the cost gaps between candidate partitions, the partition that wins on point estimates may not have the lowest expected bottleneck. This follows the paper's own warning that about 15% tail misestimation can change the selected partition. The Dynamic Bubble Optimizer cannot correct this afterwards, because it does not change partition boundaries.

- Critical link: The key step is whether per-iteration routing variation moves post-overlap pair costs by about as much as the cost gaps between competing candidates. The paper quantifies neither the variance of profiled pair costs under real routing nor the cost gaps between candidates, so the size of the effect is unknown.
- Conditions: Post-overlap costs of candidate pairs vary across iterations by an amount comparable to the cost gaps between the top candidates.; Several candidate partitions have close bottleneck costs (the tie or near-tie case).; The profiled routing distribution differs from steady-state production routing, or the selection ignores variance.; Comparison holds pipeline schedule, topology, and DBO setting constant.
- Defeaters: Profiling averages over many iterations with realistic routing, so the profiled costs already reflect expected values.; The variation averages out within the many microbatches of an iteration, so pair costs per iteration are stable.; Measured production gains with real routing (Table 2, Fig. 9 Phase 1, about 13%) show the selected partition stays better than the baseline in practice.; The cost gap between the chosen partition and the alternatives is large compared with the routing-induced variance.

## LS2-04-L2 (tessera) - applicability_limitation - mechanism_reported_consequence_inferred
**Dynamic bubble filling helps only when routing skew rotates across ranks, not when one rank stays hot**

Tessera's Dynamic Bubble Optimizer (DBO) leaves routing imbalance in place and fills the idle slots it creates with deferred movable work, mainly Wgrad. The idle slots appear on ranks that wait for a slower, hot-expert rank at All-to-All barriers, while the hot rank itself has no slots and carries more Wgrad, because expert weight-gradient work grows with the number of tokens received. DBO can shorten an iteration only if every rank, including the one that is slow at a given moment, gets idle time later in the iteration to absorb its deferred work. That holds when the hot rank changes over time. If skew persists on the same rank, for example a consistently popular expert, the bottleneck rank never receives slots, and DBO's gain may shrink to whatever it recovers from pipeline warmup and cooldown bubbles.

- Critical link: The key empirical question is how much of the hot-rank identity in production rotates and how much stays fixed. Fig. 5 shows load skew fluctuating across iterations, but not whether the same ranks stay hot. The paper also does not separate DBO's routing-slot gains from its pipeline-wait gains.
- Conditions: Routing imbalance concentrates on the same EP rank(s) over most microbatches of an iteration.; The hot rank's Wgrad cannot be absorbed into pipeline warmup/cooldown bubbles.; No external load balancer (expert replication or redistribution) removes the persistent skew.; Comparison of DBO on vs off under the same static plan and routing behavior.
- Defeaters: Production routing with auxiliary load-balancing losses keeps skew transient, so the hot rank rotates often.; Most of DBO's measured gain comes from pipeline-parallel wait (present on all ranks), which is unaffected by skew persistence.; A complementary load balancer is deployed with Tessera and removes persistent skew.; Per-rank traces show the hot rank also has usable slots (e.g., its own local bubbles from dependency waits).
- Locations: §2.3.3; Fig. 5; PDF page 5; §3.2.1-§3.2.2; Fig. 8; Algorithm 2; PDF pages 8-9; §6.6; Table 3; PDF page 14; §7 Dynamic MoE Load Balancing; PDF page 15

## LS2-05-L1 (distserve) - method_shortcoming - inferred
**Tuning prefill and decoding separately to the attainment target does not guarantee the joint TTFT-and-TPOT attainment target**

Algorithm 1 (high node-affinity placement) runs a binary search on each phase separately: simu_prefill gives a goodput for the TTFT constraint and simu_decode gives one for the TPOT constraint. It then replicates each phase to ceil(R/goodput). The paper's success metric, however, counts a request as served only if it meets both TTFT and TPOT. If each phase is sized just to reach the target (for example 90%) and the violations in the two phases are not strongly correlated, the share of requests meeting both can fall below the target (about 81% if the violations are independent). The placement can therefore be optimal for each phase and still miss the end-to-end SLO attainment it claims to maximize, unless rounding slack or correlated violations close the gap.

- Critical link: Whether the per-phase searches use the end-to-end attainment target unchanged, and how correlated TTFT and TPOT violations are under the fitted workload. Ceiling rounding of n and m adds headroom that may hide the gap at small replica counts.
- Conditions: The high node-affinity Algorithm 1 is used, not the jointly simulated Algorithm 2.; simu_prefill and simu_decode are each searched against the same attainment target as the end-to-end goal.; TTFT violators and TPOT violators are not mostly the same requests.; Replica counts are large enough that ceiling rounding gives little spare capacity.
- Defeaters: The implementation tightens each per-phase target (for example sqrt(0.9)) or validates the combined placement in a joint simulation.; Violations in both phases are driven by the same burst periods, so they co-occur and the joint attainment stays near the marginal one.; Rounding up n and m leaves enough headroom that both phases run well above their marginal targets.
- Locations: §4.1; Algorithm 1; PDF page 7; §6.1 Metrics; PDF pages 9-10; §6.4; Fig. 11; PDF page 12

## LS2-05-L2 (distserve) - applicability_limitation - mechanism_reported_consequence_inferred
**Pull-based KV transfer couples prefill throughput back to decoding capacity during sustained bursts**

DistServe handles burstiness by having decoding instances pull KV caches, so the GPU memory of the prefill instances acts as a queue buffer. The paper says this lets each instance type run at its own pace. That buffer is bounded by the prefill GPU memory left after model weights. If decoding is the bottleneck for longer than the buffer can absorb, KV caches waiting on prefill instances fill that memory and prefill can no longer admit new requests. TTFT then rises because of decode-side congestion, which the disaggregation was meant to isolate. The decoupling therefore holds only for bursts that are short or small relative to the buffer.

- Critical link: Whether real burst volume times KV size exceeds the free prefill memory, and whether the planner's per-phase replica counts leave decoding enough headroom. The paper's Poisson arrivals at a fixed rate may not create such sustained imbalance.
- Conditions: Bursts in which decoding throughput stays below prefill throughput for a sustained period.; Large per-request KV caches (MHA models, long prompts) relative to the free memory on prefill GPUs.; No cross-instance memory offload or admission control that stops prefill before its memory is exhausted.
- Defeaters: Decoding is provisioned with enough headroom that it is never the sustained bottleneck.; KV caches are small (GQA/MQA, short prompts), so the prefill buffer holds a long backlog.; Periodic replanning or autoscaling reacts faster than the buffer fills.
- Locations: §4.3 Combat burstiness; Fig. 6; PDF page 8; §3.3 Communication overhead; PDF page 6; §3.1 Eq. 1; PDF page 5; §6.1 workloads (Poisson arrivals); PDF page 9

## LS2-06-L1 (sarathi) - applicability_limitation - mixed_reported_and_inferred
**A fixed token budget bounds the token count per iteration, not its latency, once attention over long contexts dominates**

Stall-free batching caps the number of tokens per iteration at a token budget. That budget is chosen once by profiling, as the largest token count that does not violate the TBT SLO. The paper claims this bounds iteration latency and makes it nearly independent of prompt length. That holds when linear layers dominate cost, which the paper shows for sequences of up to a few thousand tokens. Attention cost per token grows with context length, both for later chunks of a long prompt (which re-read all earlier chunks' KV) and for decodes with long KV caches. With much longer contexts than those evaluated (requests over 8K/16K tokens were filtered out), the same token budget may produce iterations that exceed the TBT SLO. Alternatively, the budget has to be calibrated for the worst-case context, which lowers throughput for everyone.

- Critical link: How large attention's share of iteration time becomes for the contexts actually served. Below roughly 8-16K tokens on the evaluated models it appears small, which is why the evaluation does not show the effect.
- Conditions: Prompt or decode contexts well beyond the evaluated 8K/16K-token range.; A single fixed token budget per deployment, as in the evaluation.; A TBT SLO tight enough that context-dependent attention time matters.
- Defeaters: The budget is profiled at the maximum supported context, accepting lower efficiency.; The budget is adjusted dynamically by context length (the paper names dynamic budgets as future work; later systems shrink chunks over a prompt).; Attention kernels or sliding-window/GQA models keep attention cost small even at long contexts.
- Locations: §1; PDF page 3; §3.1 Fig. 4; PDF page 5; §4.3; PDF page 9; §5 Workloads; Table 2; PDF page 10; §5.4.1 Fig. 14; PDF page 13

## LS2-06-L2 (sarathi) - method_shortcoming - mixed_reported_and_inferred
**Decode-first packing moves interference onto prefill progress, so TTFT tails can grow with the decode batch**

Stall-free batching first packs every running decode into the budget, then any partially completed prefill, and admits new requests only with the leftover tokens. Each decode uses one budget slot. As the running decode batch grows toward its maximum, the share of the budget left for prefill shrinks, so a long prompt needs more iterations to finish prefill. Prefills therefore still wait on decodes: the interference is moved into slower prefill progress rather than removed. The evaluation defines capacity using P99 TBT and a median scheduling-delay limit, and reports median TTFT. TTFT tails for long prompts under heavy decode load are not covered by this capacity metric.

- Critical link: How much of the budget running decodes actually use at the operating point (decode batch size relative to budget), and whether TTFT tails, not medians, would bind the capacity.
- Conditions: A strict (small) token budget with a large running decode batch.; Long prompts that need many chunks.; An SLO that constrains TTFT tail latency, not only the median scheduling delay.
- Defeaters: Decode batches stay small relative to the budget at the operating point.; A relaxed SLO allows a large budget (2048), so the decode share is minor.; TTFT P99 measurements show no meaningful growth over the baselines at the reported capacity.
- Locations: §4.2; Algorithm 3; PDF pages 8-9; §5 Metrics; §5.1; PDF page 10; §5.4.2; Table 4; PDF page 13

## LS2-07-L1 (streamingllm) - applicability_limitation - mixed_reported_and_inferred
**Keeping four sink tokens stabilizes perplexity but does not keep the system prompt or task instructions once they leave the window**

StreamingLLM keeps only the first four tokens as attention sinks plus a rolling window of recent tokens, and the paper argues that the sinks matter for their position, not their meaning. In a multi-round chat deployment, a system prompt or task instruction is usually much longer than four tokens. So once the conversation grows past the cache size, everything except its first four tokens may be evicted, while perplexity stays stable. The paper's main streaming evaluations (PG19 perplexity, concatenated ARC questions that are each self-contained, and StreamEval where the answer is 20 lines back) mostly reward recent context, so they may not detect when the model drifts away from instructions that appear only at the start. Appendix D shows the matching effect on LongBench: the 4+3496 configuration loses accuracy because the initial prompt is lost, and accuracy comes back only when the sink region is widened to 1750 tokens. Widening it takes cache budget away from the recent window.

- Critical link: The key question is whether instruction-following in real chat models actually degrades once the instruction tokens are evicted, or whether recent turns and the model's in-context continuation keep the behavior going. Table 8 shows that prompt loss hurts task accuracy, but the paper has no measurement of instruction persistence in multi-turn dialogue.
- Conditions: The conversation grows longer than the cache size, so tokens past the first four of the opening prompt are evicted.; The instructions that matter appear only near the start and are not restated in recent turns.; The deployment uses the default small sink region (for example 4 tokens), not a sink region widened to cover the whole prompt.
- Defeaters: The serving system pins the whole system prompt as the sink region and the remaining recent window is still large enough.; Recent turns already reflect the instructed behavior strongly enough that the model keeps following it without seeing the instruction.; The application re-injects the instructions every turn, or is a task whose correct output depends only on recent context.
- Locations: §3.1; Table 1; PDF page 4-5; §3.2; Fig. 4; PDF page 5; §4.3; Table 5; Fig. 8-9; PDF page 8; Appendix A (Limitations); PDF page 15; Appendix D; Table 8; PDF page 17

## LS2-07-L2 (streamingllm) - mechanism_origin_unclear - mechanism_reported_consequence_inferred
**A larger cache does not consistently help StreamingLLM, and the paper does not separate model context-use limits from artifacts of its own cache-position scheme**

Table 6 shows that StreamingLLM perplexity does not consistently fall as the cache grows. For Llama-2-7B and Falcon-7B it gets worse when the cache equals the full pre-training window. For MPT-7B it gets worse at every increase. The paper attributes this to models not fully using their context. However, StreamingLLM also re-assigns positions inside the cache, and it reuses KV states that were computed when those tokens had different positions and different neighbors. These method-specific factors are not ruled out, because Table 6 has no sliding-window-with-recomputation reference at the same cache sizes. Until the cause is known, the best cache size cannot be assumed to be 'as large as memory allows', and it may differ by model and position-encoding scheme.

- Critical link: The key comparison is StreamingLLM vs sliding window with recomputation (which rebuilds states in a consistent frame) at each cache size in Table 6. If recomputation shows the same non-monotone trend, the paper's explanation holds. If it does not, the cause is in the method itself.
- Conditions: The cache is a large fraction of, or equal to, the pre-training window.; The model uses a position scheme where in-cache re-assignment differs from the positions used when the cached states were computed (RoPE re-rotation, or ALiBi contiguous bias).; Users pick the cache size assuming larger is better.
- Defeaters: A recompute baseline at the same cache sizes shows the same non-monotone perplexity, which would point to the model's context use.; Dense attention within the pre-training window shows similar non-monotonicity on PG19 at these lengths.; The effect disappears on tasks other than perplexity, or with other books or seeds.

## LS2-08-L1 (h2o) - method_shortcoming - mechanism_reported_consequence_inferred
**Permanent eviction by past accumulated attention does not guarantee keeping tokens that only a later query will need**

H2O ranks tokens by the attention they have received so far and permanently evicts the lowest-scoring one at each step. During prefill it also cuts the prompt's KV down to heavy hitters plus recent tokens. Its design rests on the observation that this local statistic works about as well as the future-aware (global) statistic. That observation comes from short 5-shot multiple-choice tasks and summarization, where the context the answer needs is usually already heavily attended while the prompt is processed. If the needed token gets little attention before the question arrives (a fact queried later, a detail mentioned once in a long document, an earlier turn referenced much later), H2O may already have evicted it, and permanent eviction means no later query can bring it back. The accuracy loss would then depend on how far later relevance diverges from earlier attention, which the paper's benchmarks do not vary on purpose.

- Critical link: The key point is whether, in realistic long-context tasks, tokens needed by later queries usually already have high accumulated attention. Fig. 2(d) supports this only for the paper's short tasks. Appendix C.4 compares H2O with StreamingLLM on multi-document QA but does not show how close it gets to full cache when the needed document gets little early attention.
- Conditions: The query or instruction that needs a token arrives after that token's KV has been processed, and possibly evicted.; The needed token receives little attention before the query arrives.; The KV budget is well below the context length, so eviction pressure is real.
- Defeaters: Measurements show that tokens later needed by queries are usually already heavy hitters when they are processed (for example salient entities or numbers).; The question is placed before the document, so prefill attention already reflects it.; H2O stays close to full cache on long-context retrieval tasks where the question comes last, at the budgets the paper recommends.

## LS2-08-L2 (h2o) - mechanism_origin_unclear - mixed_reported_and_inferred
**The paper does not establish whether heavy hitters carry task-relevant content or mainly serve as frequent or sink-like tokens that absorb attention mass**

H2O's key heuristic is that tokens with high accumulated attention are important. But the paper also reports that these scores track how often a word occurs, that many heavy hitters are at the start of sentences, and that the score favors older tokens. Attention mass can pile up on frequent, delimiter or initial tokens just because softmax must put its probability somewhere, so a high score does not by itself mean the token carries information the output depends on. The paper's main check, masking heavy hitters, would hurt accuracy under either explanation. The submodular guarantee depends on an assumed property of attention and optimizes attention-score coverage, not output fidelity. Because the reason tokens become heavy hitters is unclear, it is also unclear whether H2O's choices stay good across tokenizers, domains (such as code or multilingual text), or models whose attention-sink behavior differs.

- Critical link: The missing control would separate the two roles, for example by keeping only sink or initial tokens plus local tokens at the same budget, or by checking whether the chosen heavy hitters are content words or function and delimiter tokens. Without it, the heuristic's success cannot be attributed to keeping semantic importance.

## LS2-09-L1 (quest) - method_shortcoming - mechanism_reported_consequence_inferred
**Quest's per-channel min/max upper bound can rank pages highly with no single critical token, and the bound loosens as pages grow**

Quest scores each page by summing, over channels, max(q_i*m_i, q_i*M_i). The per-channel min and max can come from different tokens, so the score bounds an imaginary 'best-of-every-channel' key, not any real token. A page holding several keys that each match the query in a few channels can therefore beat a page holding one truly critical token. These false positives use up Top-K slots. As page size S grows (which the paper suggests to cut metadata cost), each page's min/max box widens and scores move toward a query-agnostic magnitude ranking. Large-magnitude outlier key channels would push in the same direction. Because the paper reports accuracy only for its default configuration and reports page-size sweeps only for latency, the trade-off between estimation cost (about 1/S) and selection precision is not quantified. Selection precision may drop at larger S or tighter budgets.

- Critical link: The key point is whether real key distributions within a page are coherent enough (for example, neighboring tokens having similar keys) to keep the bound tight at practical page sizes. The paper's recall (Fig. 4) and accuracy results support tightness at its default setting. How precision changes with page size and dimension was not reported.
- Conditions: Page size is larger than the default, or keys within a page are diverse.; Token budget is small, so false-positive pages displace truly critical pages.; The model's keys have channels with uneven magnitudes or outliers that inflate the bound for some pages.
- Defeaters: A sweep over page size shows recall and accuracy stay near full cache at page size 32-64.; Neighboring tokens' keys are coherent enough that the bound gap stays small in practice.; Over-provisioning K absorbs false positives at an acceptable latency cost.

## LS2-09-L2 (quest) - applicability_limitation - inferred
**Quest's memory-load reduction is not 'universal across all models': under grouped-query attention, per-query-head page choices must share KV heads**

Quest selects pages using the current query vector, and every model it evaluates (LongChat-7B, Yarn-Llama-2-7B, Llama2-7B) uses standard multi-head attention, where each query head has its own KV head. In grouped-query attention (GQA), several query heads read the same KV head. Since Quest's premise is that critical tokens depend on the query, these heads may want different pages. The implementation then either loads the union of their Top-K pages for the shared KV head, which raises memory traffic by up to the group size, or forces one shared selection, which may drop pages some heads need. GQA also already shrinks the KV cache several times over, so attention is a smaller share of decode latency, and the end-to-end gain from making attention sparse may shrink as well. So the paper's '1/PageSize + K/PageNum' saving and its 1.74-2.23x end-to-end speedups are conditional on an MHA-style layout and a single-batch setting.

- Critical link: The key question is how much the Top-K page sets of query heads in the same GQA group overlap. High overlap would make the union cheap and keep the savings; low overlap would erode them. The paper does not measure this because it evaluates no GQA model.
- Conditions: The target model uses grouped-query (or multi-query) attention.; Query heads within a group select substantially different critical pages.; End-to-end speedup is judged on decode latency, where attention's share has already shrunk under GQA.
- Defeaters: Measurements on GQA models show high overlap of per-head Top-K pages within a group.; A group-level criticality score (for example, max or sum over the group's queries) keeps accuracy at the same budget with little extra traffic.; At very long contexts (for example 128K+), attention again dominates decode even under GQA, which restores the end-to-end gain.

## LS2-10-L1 (awq) - applicability_limitation - mechanism_reported_consequence_inferred
**Per-input-channel scaling is only 'free' where the inverse scale can be folded exactly into a linear producer used by that one layer**

AWQ protects salient channels by multiplying weight input channels by s and dividing the input by s. It relies on the division being absorbed into the previous operator, which the paper says is 'usually' possible. That fold is exact and costs nothing only if the producer of X is linear (or positively homogeneous) per channel. It also must feed only the layer whose scale is being chosen. If the producer is a non-homogeneous activation such as GELU, AWQ either cannot scale that layer exactly or must add an explicit runtime scaling step. If several layers share one input (q/k/v after one norm, parallel attention+MLP blocks, or GQA value heads feeding o_proj), they must share one scale vector. In those cases the per-layer search of Eq. 4 becomes a constrained compromise, and the protection, the zero-overhead claim, or both may be weaker than in the LLaMA/OPT setting the accuracy tables cover.

- Critical link: Whether non-foldable or shared-input layers carry enough quantization error to matter. If the affected layers are few or their error is small, skipping them or using a shared compromise scale may cost little.
- Conditions: The target model has linear layers whose input comes from a non-positively-homogeneous op (e.g., GELU) or from a tensor shared by several separately quantized layers.; Those layers contribute non-negligible quantization error at the chosen bit width (e.g., INT3/INT4 g128).; The comparison holds bit width, group size and calibration fixed, and contrasts architectures where the fold is exact with ones where it is not.
- Defeaters: Implementations scale the shared input jointly and lose little accuracy compared with per-layer scaling.; An explicit scaling op is fused into an existing kernel (e.g., the dequantization GEMM) at negligible cost.; Measurements on GELU-MLP or parallel-block models show AWQ gains comparable to those on LLaMA/OPT.

## LS2-10-L2 (awq) - mechanism_origin_unclear - mixed_reported_and_inferred
**Why high mean-activation channels are salient is only hypothesized, so a static mean-magnitude scale may misallocate protection under activation shift**

AWQ ranks channel saliency by the average activation magnitude on a small Pile calibration set. It folds the resulting scale permanently into the weights. The reason these channels matter is stated only as a hypothesis: larger-magnitude features are 'generally more important'. A first-moment statistic can rank channels differently from their actual contribution to output error. This happens, for example, when a channel matters through rare, very large, token-specific activations. It also happens when deployment inputs (code, image tokens, long contexts, chat templates) activate different channels than pretraining text does. If saliency on the target distribution diverges from calibration mean magnitude, the fixed scale may protect the wrong channels. The within-Pile cross-domain test (0.5-0.6 PPL degradation on one model) does not establish how stable the pattern is under larger shifts.

- Critical link: Whether the set of high-mean-magnitude channels is stable across the input distributions a deployed model sees. If outlier channels are persistent model properties, as is often observed, the risk is small. If they are input-dependent, the fixed scale can be misallocated.
- Conditions: The deployment input distribution activates salient channels that differ materially from those of Pile calibration text.; Error on those channels is not already handled by group-wise quantization (g128) and the alpha search.; Comparisons use the same bit width and model, and vary only the calibration/deployment mismatch.

## LS2-11-L1 (vattention) - applicability_limitation - mixed_reported_and_inferred
**Fragmentation parity with PagedAttention does not hold as tensor parallelism grows, because the minimum allocation in tokens scales with TP degree**

vAttention maps physical memory per worker, per layer, per K/V tensor, in page-groups of at least 64KB. With the modified driver the minimum is 64KB; with stock CUDA it is 2MB. The number of tokens in one page-group is the page-group size divided by the per-worker bytes per token (H_worker x D x P). It therefore grows in proportion to the tensor-parallel degree, and also as KV heads per worker shrink or KV precision drops. The paper's claim that vAttention is 'as effective in reducing fragmentation as PagedAttention' rests on TP-1/TP-2 configurations where 64KB holds 32-128 tokens. At higher TP degrees, with GQA/MQA models or with FP8 KV caches, the same 64KB floor may mean hundreds of tokens per allocation unit. The 2MB fallback would mean thousands. Per-request internal fragmentation, and so the maximum batch size, may then fall behind PagedAttention, whose block size in tokens is set independently of TP. Fixing this through tensor slicing gives up per-layer contiguity and requires strided-access kernels.

- Critical link: Whether real high-TP or MQA/FP8-KV deployments have request lengths short enough, compared with the token-per-page-group count, for the extra fragmentation to cut batch size noticeably.
- Conditions: TP degree above 2, or few KV heads per worker, or a 1-byte KV cache, making tokens per 64KB page-group large (hundreds).; A workload with many short or short-lived requests, so partially filled units are a meaningful fraction of KV memory.; A memory-bound, throughput-oriented regime where max batch size determines performance.; A comparison against PagedAttention configured with a small token block size.
- Defeaters: Tensor slicing combined with small pages is used, and the target kernels support strides.; The driver adds 4KB page support for KV mappings, restoring fine granularity.; Requests in the target workload are long (e.g., tens of thousands of tokens), making per-request waste negligible.

## LS2-11-L2 (vattention) - method_shortcoming - mixed_reported_and_inferred
**Latency hiding for prefill allocation is weakest exactly where small pages are recommended: high memory pressure with variable prompt lengths**

vAttention hides the latency of CUDA VMM calls in two ways. For decode, it uses the per-iteration predictability of growth. For prefill, it reuses page-groups left behind by finished requests (deferred reclamation) and eagerly maps a few page-groups ahead. Prefill reuse covers a new request only if its prompt is no longer than the recycled slot's mapped length. Eager pre-mapping requires a pool of spare physical memory. In throughput-oriented serving near memory capacity, which is the regime where the paper recommends 64KB page-groups, both conditions may often fail. Prompt lengths vary, and the mapped-page pool is drained or reclaimed. Prefill mapping then moves back onto the critical path. That penalty is largest for 64KB pages: they have the lowest allocation bandwidth (7.6 GB/s vs 35 GB/s for 2MB) and the highest measured synchronous overhead (up to 1.15x vs 1.03x). So the fragmentation optimization and the latency optimization may partly work against each other.

- Critical link: How often, in a realistic near-capacity trace with 64KB pages, a new prefill finds neither a long-enough recycled slot nor a pre-mapped spare. The paper's ablations use single prompts or fixed-length batches and do not measure this.
- Conditions: Small page-groups (64KB) are used to maximize batch size.; The system operates near KV-memory capacity, so the cached mapped-page pool is often near or below the reclamation threshold.; Incoming prompt lengths often exceed the mapped length of recycled slots.; The comparison is against PagedAttention, whose block allocation from a pre-allocated pool needs no driver calls.
- Defeaters: Prefill mapping is also moved to a background thread overlapped with the preceding iteration, e.g., under chunked prefill scheduling.; End-to-end near-capacity traces with 64KB pages show negligible TTFT inflation compared with 2MB pages.; Prefill compute time at long contexts dwarfs mapping time, so even fully synchronous mapping costs a few percent at most.
