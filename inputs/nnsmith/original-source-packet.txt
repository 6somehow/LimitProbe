1: """
2: Class members of AbsOpBase like in_dtypes, out_dtypes, etc. are just the superset
3: of the valid domain that do not take the upcoming inference engine's operator
4: availability into account. For example, older versions of TVM may not support trilu
5: and TensorRT does not accept a 2D Pool whose kernel is larger than 300. Therefore,
6: to narrow those specifications, we look at the following methods:
7: - Identifier: Model and BackendFactory
8: 1. Single-operator specification testing: Iterate over possible operator instances
9:    of available `data types` (and `ranks`), and try to kick out failing ones (loggings
10:    will be kept to see if it is just an unimplemented feature or a bug).
11: 2. Constraint extension: for a BackendFactory, it can add more constraints to an operator.
12:    This is useful for cases like TensorRT where the kernel size is limited to < 300.
13: - HOWTO:
14: 1. Single-operator potential data types (and ranks) are serializable as a JSON file.
15: 2. Constraint extensions are defined as Python codes. That said, we can just overload the
16:    operator specifactions in backend (see nnsmith/abstract/extension).
17: """
